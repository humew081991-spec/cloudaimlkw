Why You Can't Read LangChain
Without Understanding Classes

July 2026 · 6 min read

Every major AI framework — LangChain, LlamaIndex, CrewAI, LangGraph — is written in object-oriented Python. That is not incidental. It reflects a design principle that determines whether an engineer can extend these frameworks or is limited to copying examples from documentation. The distinction matters more than most AI onboarding material admits.

Two ways to bind logic together

In Python, there are two fundamental ways to group related statements: a function and a class. A function binds a set of statements under a single name — call the function, the statements execute. A class does something different: it binds functions and data together into a single reusable structure, and requires instantiation before use.

The natural question is why a class is necessary at all when a function already provides encapsulation. The answer becomes obvious once the system has more than one related capability that needs to share state.

Consider a banking account. A function can check a balance. A separate function can process a debit. A third can process a credit. Each works in isolation. But the moment these three operations need to share the same account balance — consistently, across every operation, for every individual account — a function alone cannot hold that state. A class can. It binds the balance (the data) and the operations that act on it (the methods) into a single unit, and every new account becomes a new, isolated instance of that unit.

Why this is exactly how AI frameworks are built

Open the source of any serious AI framework and the same pattern repeats. An agent in LangChain is a class. A retriever in LlamaIndex is a class. A node in LangGraph is a class. Each holds internal state — memory, configuration, connection details — and exposes methods that act on that state.

This is why an engineer who understands functions but not classes can copy a working example from documentation, but struggles the moment they need to customise behaviour beyond what the example shows. Extending a framework means understanding what state a class holds, which methods are meant to be overridden, and how inheritance is being used to share common behaviour across related components.

Inheritance is how frameworks avoid repeating themselves

Inheritance lets a new class reuse the structure of an existing one while overriding only what needs to differ. A practical way to see this: imagine a base vehicle class holding features every vehicle shares — four wheels, an engine reference, a manufacturing year. A petrol vehicle and an electric vehicle both inherit that shared structure, but each defines its own refuelling behaviour — one pumps fuel, the other charges a battery.

AI frameworks use this pattern constantly. A base agent class defines the core reasoning loop — observe, plan, act, reflect. Specific agent types inherit that loop and override only the planning logic — a research agent plans differently than a coding agent, but both share the same underlying execution structure. Recognising this pattern when reading framework source code is the difference between confusion and clarity.

Polymorphism — why the same method name means different things

A related concept worth understanding is polymorphism — the ability for different classes to implement the same method name with different behaviour. A shape's area calculation differs entirely between a circle and a rectangle, but both expose an area method. The calling code does not need to know which shape it is dealing with — it simply calls the method appropriate to the object it has.

This is exactly how AI frameworks let different tools, retrievers, or agents be swapped interchangeably. A workflow built around a generic "retrieve" method works identically whether the underlying retriever is querying a vector database, a SQL database, or a file system — because each retriever class implements that method according to its own logic, while presenting the same interface to everything that calls it.

The other half of production AI: model persistence

A separate but equally practical concept for infrastructure teams evaluating AI deployments is model persistence — how a trained model's state is saved so it does not need to be retrained every time it is used.

There are three common formats, and the choice between them has real infrastructure implications:

Pickle

Python's native serialisation format. Simple and fast for small to medium models, but not designed for large datasets and carries security considerations — deserialising an untrusted pickle file can execute arbitrary code.

Joblib

Built for larger objects with significant numerical data — the standard choice for scikit-learn models with substantial parameter arrays. More efficient than pickle at scale, though the same trust considerations apply.

ONNX

An open, framework-independent format designed for secure, portable model deployment. The right choice when a model needs to move between environments, be served by a different runtime, or when the deployment context requires stronger security guarantees than pickle or joblib provide.

For infrastructure teams, this decision affects storage architecture, API design, and how models are versioned and rolled back — the same operational disciplines already applied to application deployments now need to extend to model artefacts.

What this means in practice

Infrastructure teams evaluating a move into AI delivery sometimes assume the learning curve is entirely new territory — unfamiliar mathematics, unfamiliar tooling. In reality, the software engineering foundation is the same discipline that has always underpinned reliable systems: understanding how state is held, how behaviour is shared and overridden, and how components expose consistent interfaces to each other.

Teams that already have strong object-oriented fundamentals from infrastructure automation, API development, or platform engineering are closer to being AI-framework-ready than the marketing around AI tools tends to suggest. The gap is not conceptual. It is exposure — knowing which patterns in the code they are about to read map to concepts they already understand.
