Migrating to Microsoft Entra ID — the parts nobody warns you about

Entra migrations look clean on paper. In practice there are licensing traps, legacy authentication dependencies, and conditional access conflicts that surface at the worst moments.

Every Entra migration I've run starts the same way: a stakeholder sees the Microsoft documentation, decides it looks straightforward, and books a two-week project window. By week three we're still untangling legacy authentication protocols and nobody's happy.

This isn't a criticism of Entra — it's a genuinely capable identity platform. But the migration path from an on-premises Active Directory environment is rarely as linear as the documentation makes it appear.

The licensing conversation you need to have first

Before touching a single identity, you need to be clear on licensing. Conditional Access — the feature most organisations cite as the primary reason to migrate — requires Entra ID P1 at minimum. MFA registration policies, Identity Protection, and Privileged Identity Management (PIM) require P2. In environments with a mix of user types, the licensing cost per user often comes as a surprise.

The trap is that Microsoft 365 E3 and E5 bundles include Entra P1 and P2 respectively — but only for users who are licensed for those SKUs. Service accounts, shared mailboxes, and on-premises-only users fall into a grey zone that needs careful scoping before you commit to an architecture.

Legacy authentication — the thing that breaks everything

Legacy authentication protocols (NTLM, Basic Auth, older SMTP AUTH implementations) don't work with Entra's modern authentication flows. This is by design — they're security risks. But in a typical large environment, there are applications using them that nobody documented.

  • Old line-of-business applications authenticating against Exchange with Basic Auth
  • Printers, MFDs, and IoT devices using SMTP relay with Basic Auth
  • Third-party monitoring tools using NTLM against internal services
  • Scripts and scheduled tasks using credential-based authentication

The discovery phase for this is non-negotiable and takes longer than expected. Entra's Sign-in Logs with the "Legacy authentication" filter is your starting point, but it only shows what has authenticated recently — not what's dormant and will break on cutover.

The best time to audit your legacy authentication dependencies is six months before the migration. The second best time is right now.

Hybrid identity design decisions that matter

Most enterprise migrations go through a hybrid phase — Entra Connect Sync keeping on-premises AD and Entra ID synchronised — before any full cloud-only transition. The decisions you make here are sticky:

Password Hash Synchronisation vs Pass-Through Authentication: PHS is simpler operationally and enables leaked credential detection. PTA keeps authentication on-premises (required in some regulatory environments). Federated identity (ADFS) is increasingly hard to justify given its operational overhead.

UPN suffix alignment: Your on-premises UPN suffix (user@contoso.local) almost certainly doesn't match your verified domain in Entra (user@contoso.com). Fixing this before sync starts is much easier than fixing it after.

Scoped synchronisation: Start by syncing a pilot OU, not the entire directory. The first sync always surfaces objects with unexpected attributes, duplicates, or synchronisation errors that need resolution.

Conditional Access — start permissive, tighten gradually

The instinct is to deploy Conditional Access policies in blocking mode from day one. Resist it. Use Report-Only mode for the first two to four weeks. The volume of legitimate authentication flows that would have been blocked — because of registered devices, network locations, or app registrations that weren't accounted for — is consistently higher than anyone expects.

A staged approach: Report-Only → Block legacy auth only → Require MFA for admins → Require MFA for all users → Require compliant device → Require managed device. Moving through these stages with a two-week observation window at each step catches the majority of issues before they become incidents.

What the end state looks like

A well-executed Entra migration lands in a place where on-premises AD becomes a thin synchronisation source rather than the identity authority. Authentication decisions move to Entra, device management moves to Intune, and the conditional access policy set becomes the primary security control for identity. That's a genuinely better security posture — it's just the path to get there that needs careful management.
